> **In one sentence.** A transformer turns each token into a vector, lets every position look at every earlier position, pushes the result through a big learned function, and repeats that a few dozen times before guessing the next token.

You do not need to implement a transformer to collect one, but you need
its shape to read a `config.json`, to size a KV cache, and to know why a
"235B" model can run at the speed of a 22B. This is that shape, with the
numbers attached.

## Tokens and the embedding

Text arrives as **tokens**: pieces of words from a vocabulary of a hundred
thousand or so, chosen by the tokenizer so that common words are one
token and rare ones are several. Each token id looks up a row in the
**embedding** table, a vector of `hidden_size` numbers, 4,096 for an 8B
model, 8,192 for a 70B. From here on the model works only with vectors.

The embedding is `vocab_size × hidden_size`: 150,000 × 4,096 is 600
million parameters, or about 8 percent of an 8B model. At the other end,
the **output head** turns the final vector back into a score per vocabulary
entry; many models tie it to the embedding to save the space.

## A block

A model is a stack of `num_hidden_layers` identical **blocks**, 32 for an
8B, 80 for a 70B. Each block does two things to every position's vector,
with a normalization and a residual connection around each:

1. **Attention** lets the position gather information from earlier positions.
2. The **feed-forward network** (the MLP) transforms the gathered vector with two large matrices and a nonlinearity between them.

The MLP is the bulk of the parameters: `hidden_size × intermediate_size`
twice or three times, with `intermediate_size` around 3.5× the hidden
size. Attention is the rest. For a dense 8B model, a block is about 218
million parameters, and 32 of them are 7 billion.

## Attention, heads, and the KV cache

Attention computes, for each token, three vectors: a **query**, a **key**,
and a **value**. The query is compared against every earlier key; the
matches weight a sum of the earlier values. Done `num_attention_heads`
times in parallel, each head with `head_dim` numbers, so 32 heads × 128
is the 4,096-wide hidden size again.

During generation the model produces one token at a time, and every
token's key and value are needed by every later token. Recomputing them
would be quadratic, so runtimes keep them: the **KV cache**. Its size per
token is

> 2 × layers × KV heads × head dimension × bytes per number

The "KV heads" is the number that has changed most in five years.
**Multi-head attention** had as many KV heads as query heads. **Grouped
query attention** (GQA) shares each KV head among a group of query heads,
so an 8B model with 32 query heads keeps only 8 KV heads and its cache is
a quarter the size. **Multi-head latent attention** (MLA), from DeepSeek,
stores a single compressed latent per token, 512 to 576 numbers, and
reconstructs keys and values from it, cutting the cache by an order of
magnitude again.

| Model shape | Layers | KV heads × dim | KV per token, F16 | 128k context |
|---|---|---|---|---|
| Old-style 7B, MHA | 32 | 32 × 128 | 512 KiB | 64 GiB |
| Modern 8B, GQA | 32 | 8 × 128 | 128 KiB | 16 GiB |
| Dense 70B, GQA | 80 | 8 × 128 | 320 KiB | 40 GiB |
| 671B, MLA | 61 | latent 576 | 69 KiB | 8.6 GiB |

That last column is why long context is a memory problem before it is a
compute problem, and why the runtimes offer to quantize the cache to
eight or four bits. The [Memory Lab](/docs/learn/numbers/#the-memory-lab)
sizes it for any shape.

## Position: RoPE and the context window

Attention itself has no idea which token came first. Position is injected
by rotating the query and key vectors by an angle that depends on the
token's index: **rotary position embedding**, RoPE. A model trained on
8,192-token sequences has only ever seen rotations up to that far, and
degrades past it. Context extension methods (YaRN, NTK scaling, the
`rope_scaling` block in `config.json`) stretch the rotation schedule so a
model trained short can attend long, usually followed by a little more
training to settle it. A "128k context" model is one that was trained or
extended to that length; whether it *uses* the far end well is a separate
question benchmarks answer.

## Mixture of experts

A **mixture-of-experts** model replaces each block's single MLP with many,
the **experts**, and a small **router** that sends each token to a few of
them. `Qwen3-235B-A22B` has 235 billion parameters on disk and activates
22 billion for any one token: 8 of its 128 experts per block, plus the
attention and the shared parts. Two consequences:

- **Disk and memory scale with the total.** Every expert must be present, because the router may pick any of them. A 235B MoE needs 235B worth of bytes loaded, even if most sit idle on any given token.
- **Speed scales with the active count.** A token reads only the experts it was routed to, so bandwidth per token is that of a 22B model. This is the trick that makes trillion-parameter models servable.

The name carries both numbers, and darsay reads them from it: the **MoE**
lens on a board is `-A22B` and its relatives.

## Vision, audio, and the projector

A multimodal model is usually a text transformer with a separate
**encoder** (a vision transformer, an audio model) whose output is passed
through a small **projector** into the language model's embedding space,
so an image becomes a few hundred tokens the language model reads like any
others. In GGUF repositories the encoder and projector ship as `mmproj-*.gguf`
beside the language weights. The language model alone is a text model;
the projector alone does nothing. Collect the pair.

## Drafts and heads

A model generates one token per forward pass, and a pass over 70B
parameters is mostly time spent reading them. **Speculative decoding**
puts a small **draft** model in front: it proposes several tokens cheaply,
the big model checks them all in one pass, and keeps the longest correct
prefix. The output is exactly what the big model would have said, sooner.
The draft is a separate small model with the same tokenizer, or a trained
head (EAGLE, Medusa) bolted to one specific target, or **multi-token
prediction** layers shipped inside the main weights. On a board, the
**speculator** lens is the first two; the third comes with its model.

## Reading a config

```json
{
  "hidden_size": 4096,
  "intermediate_size": 14336,
  "num_hidden_layers": 32,
  "num_attention_heads": 32,
  "num_key_value_heads": 8,
  "head_dim": 128,
  "vocab_size": 128256,
  "max_position_embeddings": 131072,
  "rope_scaling": { "rope_type": "llama3", "factor": 8.0 },
  "torch_dtype": "bfloat16"
}
```

Eight lines and you can price the model: about 8 billion parameters, 16
GiB in BF16, a 128 KiB KV entry per token, and a context that was
extended eightfold from what it was first trained on. darsay reads this
file when it prices a row.

## Where this bites

- **KV cache is the second model in memory.** A 70B at Q4 is 40 GiB; its cache at 64k context is another 20 GiB in F16. Runtimes fail to load, or quietly shrink the context, when the cache does not fit.
- **MoE is not small.** "22B active" is a speed, not a size. The vault holds 235B.
- **Head dimension is not hidden ÷ heads anymore.** Recent models set `head_dim` explicitly and larger. Read it, do not derive it.
- **Context claims are training claims.** A model can accept 1M tokens and have been trained on 32k of them. The config says what it accepts; the card says what it was trained for.
